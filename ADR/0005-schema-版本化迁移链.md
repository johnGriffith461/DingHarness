- 依据（本地代码与实测）：`engine/adapters/sqliteStore.ts`（改造前只有 `PRAGMA user_version` 一处判据）、

- 外部参照：V5 实施方案 §3.1（三层迁移策略与回滚细节）、§3.2b（目标 schema 草案）、
  FastClaw 用迁移表 + 租约表管 schema 演进（`docs/sandbox-pool-leases.md`）、
  OpenBitFun relay 的 `ClientOutdated`（版本不匹配 → **不可重试**的拒绝，而不是"尽力而为"）。

## 背景

会话库的结构演进在此之前**有版本、没有链**：`prepareSearchIndex(db, SCHEMA_VERSION)` 里
一个 `if (addedBody || userVersion < schemaVersion)` 把"补列 + 回填 + 写版本号"三件事
糊在一起。加第二步迁移时它会变成 `if v < 3 … if v < 4 …` 的意大利面，而且**没有任何地方
能回答"这个库经历过哪些版本、什么时候"**。

V5-1 马上要往里加东西（actor 维度 / owner / 成员与审批表），而这一层的失败形态是
**静默改坏数据**（少一段历史、把三年的事件全挤进今天、把新结构按旧口径解释）——
所以先把迁移机制本身做对，再加字段。

## 决定

### 1. 有序迁移链，**只增不改**

`engine/adapters/sqliteSchema.ts` 的 `MIGRATIONS`：版本号**连续**（1..N，测试守卫钉着），
每一步只做"加"（新表 / 新列 + 回填）。删列、改名不许直接做 —— 要走
"先加新的 → 双写一段 → 再移除"的三步，且必须带 ADR。

`SCHEMA_VERSION` **不手写**，取 `MIGRATIONS` 最后一步的版本：新增一步忘了改常量 =
版本号与链各说各话，那种错没人会发现。

### 2. 账本：`schema_version(version, name, applied_at)`

比 V5 §3.2b 草案多一列 `name`：读账的人不该为了知道"v2 是什么"去翻代码。
`version` 是 PRIMARY KEY（重跑天然幂等）。

⚠️ **同时继续写 `PRAGMA user_version`**：它是"迁移表上线之前那代程序"唯一认识的版本记录 ——
降级闸门必须同时看它，否则"老程序打开新库"这一路会漏（老程序不认账本表）。

### 3. 不可降级：库比程序新 → **拒绝读写**

`SchemaDowngradeError`，消息里带两个版本号与"怎么做"（用新版程序打开 / 备份后改名）。
不做"尽力读一边"：新结构里的列（比如 `actor_kind` 的取值集合）按旧口径解释就是**静默损坏**，
而"读得到但意思是错的"比"读不到"难发现得多。参照 OpenBitFun relay 的 `ClientOutdated`：
版本不匹配是**不可重试**的拒绝，其余拒绝才保持可重试。

闸门看得见的三个来源取**最大**：账本、`PRAGMA user_version`、表在不在
（最老那代库两表建出来了、却没有任何版本记录 → 至少算 v1）。

### 4. 老库"认领"（adopted），如实标出

迁移表上线之前建的库，按上面的三条线索反推它已走到哪一版，补记账（`applied_at` = 记账时刻）。
`MigrationReport.adopted` 与 `applied` **分开报** —— "这次真跑的"与"认领来的"是两件事，
日志与测试都靠这个区分（认领不该被说成迁移过）。

### 5. 每步一个事务；失败**停在旧版本**

`BEGIN IMMEDIATE` → 干活 → 记账 → 推进版本 → `COMMIT`；失败 `ROLLBACK` 并抛
（消息里带"库停在 vN，旧数据未动"）。实测：SQLite 的 DDL 也是事务性的，
失败那一步**建的半张表会整个消失**（比"表在但空"更干净）。

### 6. 迁移前自动快照（V5 §3.1）

宿主（`createSqliteSessionStore`）在**真有 pending 且盘上本来就有东西**时，
把库文件复制成 `<库名>.pre-migrate.bak`（覆盖式，一份就够 —— 链只在升级那一刻跑）。
判据是"**打开之前**文件字节数 > 0"：`openSqlite` 会建文件、还会切 WAL 写库头，
打开之后再量，全新库也是 4KB（第一版就这么把空文件也备份了一份，测试当场逮住）。

备份**不拦迁移**：它是保险，闸门是第 5 条那个"失败即回滚"。

### 7. 与历史迁移的分工（任务 3.3b 的正面回答）

仓里有两代迁移，各管一层，**不许互相替代**：

| 谁 | 管什么 | 形态 | 调用方 |
|---|---|---|---|
| `migrateJsonlSessions`（Phase 12 / 4.3）与桌面侧 `migrateLegacyJsonl` | **存储格式换代**：旧 `.jsonl` 文件 → 库 | 读旧写新**不删旧**、幂等、按会话 id 去重 | 宿主（桌面启动 / CLI） |
| 本模块（迁移链） | **库内的表结构演进**：加列 / 加表 / 回填 | 有序、版本记账、不可降级 | `createSqliteSessionStore` 打开时 |

顺序固定：**先换代（数据进库）、再演进（库内升版）**。两者不会互踩：换代只 `append`
（不碰结构），链只碰结构（不动既有行 —— 除回填那种"只补空串"的活）。

## 回退策略（对齐 V5 §3.1 的回滚细节）

| 情形 | 怎么退 | 为什么可行 |
|---|---|---|
| 迁移**没跑完**（某步抛错） | 什么都不用做：事务已回滚、库停在旧版本、旧路径照旧可用 | 第 5 条；只有 `schema_version` 账本行可能少记（那是记账，不是数据） |
| 迁移**跑完了**、但发现有问题 | 用**旧版本程序 + `.pre-migrate.bak`** 覆盖回库文件 | 第 6 条；旧程序只认 `PRAGMA user_version`（备份里的版本是旧的） |
| 新字段已写入**真实值**（V5 以后：如 `owner` 是真实成员） | **不回滚数据，只回滚语义**：把该列置回默认值；真实值留在事件流里，C5 完成后可从 actor 维度恢复归属 | V5 §3.1 的口径 |
| 触发条件 | 48h 熔断或用户指令 | V5 §8 的施工纪律 |

**CI 守卫**：迁移只许前进 —— "库里的版本不许比仓库里 `SCHEMA_VERSION` 降级"
（3.10b 的契约 diff 门一并做）。

## 明确不做的

- **不引迁移框架/库**（knex/prisma 那类）：这个库只有两张业务表，引入一整套迁移运行器
  换来的是又一个依赖与一层不透明的语义；我们要的"有序 + 记账 + 不降级"一百多行就够，
  而且**读得完**。
- **不做自动降级转换**（新库 → 旧结构）：转换代码本身没人测（用户永远不该走那条路），
  却要在每次结构变更时维护 —— 收益为负。
- **不做"迁移时自动清理"**：迁移只搬不改（`prune` 是另一条显式路径，见 `sqliteStore` 的口径）。

## 后果

- 加一步迁移的成本 = 在 `MIGRATIONS` 末尾加一个 `{version, name, apply}` + 一条能红的测试。
  版本号、账本、降级闸门、备份都是自动的。
- **老库升级这件事从此可复盘**：`schemaLedger(db)` 能读出"哪一版、什么时候、叫什么名字"
  （CLI 排查与 Qoder 审计都用得上）。
- 已知边界（如实记）：账本里"认领"那几行的 `applied_at` 是**记账时刻**，不是当初真正应用的时刻
  —— 那段历史在旧程序里根本没记，编一个时间等于伪造证据。
