- Open follow-ups：
  · **不做删除/改写**：同步的是"发生过的事"，日志只追加；
  · 一次一轮（无常驻循环）：要一直同步就配定时任务；
  · 热协作（两端**同时**编辑同一张画布）仍不在这一层 —— 见 ADR-0016 §6。

## 背景

V5-2 之前只有"引擎原语 + 中继 + 服务端端点"：协议、游标、出站队列、fencing 齐了，
**验收口径也达标**（乱序/重复/断线三态 fixture、双端 fencing、多实例竞态都有测试），
但**没有一个宿主在推拉** —— "两台设备同步同一段会话"作为产品功能并不存在。
ADR-0016 §1 那句"恢复规则是给将来那个客户端写好的"说的就是这一格。

## 决定

### 1. 同步的单位是**记录**，不是事件

`TurnEvent` 是**界面投影**（没有 `requestId`、没有 `at`），而另一端要的是"能直接 append 的
那一条"。这个项目的立场是**日志即真相** —— 所以帧的载荷是**记录 + 它自己的 `at`**。
一句话：**中继搬的是日志，不是投影。**

### 2. 帧 id 是**内容寻址**，不是 `(生产者, 本地 seq)`

```
id = sync#<会话 id>#<FNV-1a(canonical(记录去掉 seq))>
```

第一版拼的是 `(生产者, 本地 seq)`，测试当场推翻：**B 把 A 的记录合并进自己库、再推出去时**，
那些帧带着 B 的编号 —— A 拉回来认不出"这是我的内容"，于是**又 append 一遍**（一份内容
在多跳之后变成两份）。换拼法救不了"转手"：中转站不可能知道原本该用哪个编号。

内容寻址把这件事变简单：**id 是内容的函数**，一份内容不管走几跳、由谁推，id 都一样。
由此两条推论：
· **"是不是我的"= 本地库里有没有这份内容** —— 不需要单独的"已应用账本"（应用过的就在库里）；
· 去掉 `seq`（本机编号，两端不同）但**留着 `at`**（事实，且两端互传时原样保留）——
  两条内容相同而时刻不同的记录（比如两次一模一样的 `done`）因此不会被误当同一件事。

⚠️ FNV-1a 不是密码学哈希（不必是：它只用来去重；防篡改是签名与 E2EE 那一层的事）。

### 3. 一轮同步的顺序：建流/claim → 推自己 → 拉别人

· 推之前先 `claim`（拿**当前** epoch）：中继是"单一持有者 + fencing"，另一端接管过的话
  直接推会拿到 `fenced`；
· 中继回 `gap`（换流/换实例）→ `pushedSeq` 清零**从这条流的头重推**（ADR-0016 §1）——
  内容 id 不变，所以另一端按 id 去重、不会重复；
· 拉回来的记录 `at` 用记录自己的（不是"现在"）—— 另一端的历史不该被挤进我这一刻。

### 4. 归属（C1）不在这一层判，也**不猜**

合并只回答"哪些该 append"。**能不能写这段会话**是宿主的门（服务端 `canWriteSession`、
桌面的归属校验）。本地没有这段会话时：要么它已经在本地（先同步过来），
要么显式 `--owner <成员 id>` —— **不给就拒绝**（归属是 C1 的事实，不该由同步顺手编一个）。
