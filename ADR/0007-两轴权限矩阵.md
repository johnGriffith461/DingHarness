  只记它的两条原则：策略是数据、拒绝优先。

## 背景

权限此前只有**一轴**：工具档位（「全部允许 / 按需确认 / 每步确认」）——
它回答"我信这个模型多少"。V5 的 C2 要求补上**人轴**（成员角色）：它回答"这个**人**是谁"。

两轴必须**在同一层**表达且叠加语义无歧义（V5 §1 的新增不变量），否则会出现
"同一个动作在两条路上两种判定"——仓里已经吃过这个形状的亏（审计 P02：
MCP 工具按"写"拦、插件工具却掉进"默认只读放行"，两道闸里弱的那个就是实际生效的那个）。

## 决定

### 1. 叠加矩阵（唯一权威，逐格有测试）

| 工具轴 \ 人轴 | owner | admin | specialist | viewer |
|---|---|---|---|---|
| `hide`（工具没注入给模型） | hide | hide | hide | hide |
| 只读 + `run` | run | run | run | run |
| 只读 + `ask` | ask | ask | ask | ask |
| 写 + `run` | run | run | run | **deny** |
| 写 + `ask` | ask | ask | ask | **deny** |

三句话概括（实现与测试都从这三条推）：

1. **角色是上限，档位是旋钮**：档位只能在角色允许的范围内收紧或放松。
   所以 viewer 的写操作在「全部允许」档下**也拒** —— 那一档说的是"我信这个模型"，
   不是"改写文件的人是谁"。
2. **`hide` 与角色无关**：工具没注入，模型根本不知道它存在 —— 跟"谁在用"没关系。
3. **只读不受人轴影响**：拦只读只会让只读成员什么都干不了（而只读本身不改变任何东西）。

### 2. 角色最小集与兜底

`owner | admin | specialist | viewer`（V5 §3.6 的原文）。

- **空角色 = viewer**（最小权限方向：身份在、还没被授予任何东西时不该拿到写权）；
- **未知成员**（查不到这个人）由调用方决定：
  · **本机单用户阶段 = owner** —— 老路径（不给 `memberRoles`）行为一字不变，
    这是 V5 §1"身份向后兼容"在权限层的落点；
  · ⚠️ **V5-2 把成员 token 映射接上之后，"未认证/查不到"一律按 viewer**
    （多用户系统的安全默认）。这条切换是**行为变更**，到那时要单独写进变更记录 ——
    实现里那句 `member ? rolesOf(member) : ["owner"]` 的注释就指着这里。

### 3. `deny` 与 `ask` 是两回事

- `ask`：工具轴要问 → 交用户确认，**没执行**，等一个决定；
- `deny`：人轴不够 → **没执行、也不等人批**，直接回注人话（走"错误即结果"那条路：
  抛错 → 投影算 `ok=false` → 模型拿到原因）。

为什么不让 viewer 的请求落到 `ask`：那会把**权限问题伪装成审批问题** ——
用户点了"允许"也不该生效（点了就生效 = 权限墙是假的；点了不生效 = 界面在骗人）。
两条都是坏结果，所以在这一层就分开。

回注话术（`viewerDeniedNotice`）必须同时给"为什么"与"下一步"：模型能做对的事只有
两件 —— 停下、或者把事交给有权限的人。

### 4. 人那一侧的能力表（`CAPABILITIES`）

本轮只有 `manageMembers`（owner/admin 有，specialist/viewer 没有）。
**审批裁决权不在这里** —— 它是 3.7（C3）的一部分（审批人集合），由 ADR-008 定；
两处各写一套"谁能批"就是这一层最该避免的那种漂移。

### 5. specialist 与 admin 在工具上**同权**

不编"工具 → 专业方向"的映射：没有那个映射时把 specialist 编窄一点，
只是凭空发明规则（而它会直接改变谁能在真实机器上写文件）。
两者的差别落在**人**那一侧（能不能管成员）。

## 明确不做的

- **不做工具级细粒度 ACL**（文件路径 / 网络出站 / 端口那种多维声明，FastClaw
  `policy.go` 的形状）：那要到有真实多用户场景（不同成员该看到不同目录）时再加；
  现在引它 = 一整套没有人用的规则语言。**参照物已记在这里**，别重新调研一遍。
- **不做按空间分域的角色**（`member_roles.scope`）：V5-3 团队空间落地时再说。
- **不改工具轴本身的语义**（三档的名字与 read/write 判定照旧）：本轮只在外面**乘**一层人轴，
  工具轴的既有测试逐条不动 —— 这是"叠加"而不是"重写"的证据。

## 后果

- 判定是**纯函数**（`decideForMember(member, mode, name)`），矩阵逐格有断言；
  执行点的接线（deny 抛错）也有断言。
- 老路径零变化：不给角色 = owner = 与从前逐字相同的判定（测试里对照 `decide` 验证）。
- 已知边界（如实记）：
  · **`hide` 目前没有产品入口**（没有任何内置工具是 `enabled:false`）——
    判定支持它、测试用临时策略条目覆盖它，但用户现在无法把一个工具"关掉"；
  · 成员目录只在内存里（`createMemberDirectory`），没有持久化 —— 见 Open follow-ups。
