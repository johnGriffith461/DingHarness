## 背景

V5-2 要支持"拿一段会话（或一张画布）去评阅/试跑"：评审者需要与原件**一模一样的上下文**，
但不该动原件、也不该让原件此后的变化影响他看见的东西。

两个决定要定死：**副本与原件的隔离边界**，以及**"副本里有历史动作"这件事怎么说清楚**。

## 决定

### 1. fork = 独立副本，逐轮投影必须一致

副本 = 源记录的**复制**（`forkSession`）：`at` **原样保留**（那是"当时说的"，
不是"复制那一刻发生的"），`seq` 剥掉由存储重新发号（编号是存储的事）。
"分叉那一刻一模一样"的判据是**逐轮投影相同**（`forkReplaysEqual`）——
不是"记录字节相同"（`seq`/`requestId` 两边本来就不同）。

### 2. 副本与源**此后的变化互不影响**

两段独立的会话各自追加、各自演化 —— fork 不是"软链"（那会让"评阅"变成"看实时"）。
出处只记在 `sessions.forked_from`（可空），**源会话那一侧一个字都不改**（测试钉着）。

⚠️ 为什么出处不写进记录里：加一种记录类型是一次**契约变更**（ADR-0010 的门要求留名），
而"从哪来"是**会话级元数据**（与 title/owner 同一层）—— 放对了地方就不必动契约。

### 3. 副作用警示**随行**（fork-for-review 的必需品）

记录是惰性的：回放它**不产生任何副作用**。但副本里那些 `tool-call`/审批留痕是**历史**，
不是"待办"—— 接着跑（或重跑某一轮）会真的再执行一次（写盘、发消息、跑命令）。

所以 `forkNote(...)` 给一句白话，三件事说清：从哪来（源会话 id）、带着什么
（数了"N 次工具调用、M 条审批留痕"）、回看与接着跑的区别。界面显示它，
**测试钉着这几句**（`回看.*不产生`、`接着跑|重跑`）。

### 4. 迁移 v5：`sessions.forked_from`（可空，不编默认值）

NULL = 不是分叉来的。**不给空串默认值**：空串会被读的人当成"从某个空 id 分出来的"。
老库补列之后读出来源仍是 undefined ✓（兼容口径）。

### 5. 顺带补强了契约门（3.10b 的洞）

加 `forkedFrom` 时发现：契约门第一版**只比"键"不比"值"** ——
"给 `SessionSummary` 加一格字段"这种改法一点都不红（变异实证当场逮住）。
现在门：① 键两向对账；② **逐字比值**（改一个字也红）；③ 每项的 ADR 真实存在；
④ 关键行为面当面复算。冻结清单同时补两个面：`record.types`（`parseLogLine` 认的类型表）
与 `session.summary.fields`（会话摘要的字段集）—— 它们各自是"加一种记录类型 /
加一格摘要字段"的哨兵。

## 明确不做的

- **不做"重跑副本里的某一轮"的自动化**：那会把"副作用警示"变成"副作用开关"，
  而它该是人工动作（ADR-0008 的一次性允许语义同理）。
- **不做复制时的裁剪**（"只留最后 N 轮"之类）：fork 的卖点就是**一模一样**；
  要裁剪是另一个功能（导出/摘要），别混进来。
- **不改记录类型表**（见决定 2 的理由）。

## 后果

- "拿去看"有了正确的工具：副本独立、出处可查、警示随行；源会话零改动。
- 契约门比 2.5 之前更硬（值比对 + 两个新哨兵面），往后的契约改动手滑都会被拦住。
- 已知边界（如实记）：分叉来源只有**一层**（副本的副本不追链 —— 只记直接来源）；
  界面上还没有入口（V5-3 3.2）；画布侧的分叉要等 V6 的事件化写入。
