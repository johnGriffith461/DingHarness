- 日期：2026-10-17
- 状态：**已决定（已落地）**
- Decision owner：Zcode（V5 收尾）
- Reviewed by：不用管（主人 2026-10-17 明确）
- Commits：与实现同笔提交（`engine/sync/sealed.ts` + `merge.ts` 的密钥化 id + `hosts/cli/cmdSync.ts`）
- 依据：ADR-0014（E2EE 内容层与明文控制层）、ADR-0017（同步客户端与合并语义）、
  M3 的结论（零知识与审批路由不相容）

## 背景

ADR-0014 定了"内容加密 / 控制明文"，`sealContent`/`openContent` 也在、测试也有；
但 ADR-0017 那一轮做的同步客户端**推的是明文** —— 也就是说"两台设备同步一段共享会话"
服务端看得见内容。承诺了一半，这一条把它接上。

## 决定

### 1. 分两类，判一次

| 哪一类 | 怎么走 | 依据 |
|---|---|---|
| 内容（`request` / `text` / `tool-call` / `tool-result` / `done` / `error` / `delegation`） | **封起来** | 用户的东西，中继不该看见 |
| 控制（`approval` / `approval-grant` + `e2ee.CONTROL_EVENT_TYPES`） | **明文** | 审批与接管要能被**路由**（零知识与"云端帮你路由审批"天生不相容） |

判断只有一处：`sealed.isSealedRecord(type)` —— 两端都问它。各写一份的话，
"一端封了、另一端按明文读"会表现为"另一端少了一段历史"（最难查的形状）。

### 2. 帧 id 掺密钥（**不给密钥的人连 id 都算不出来**）

内容寻址的 id 在明文房间里是内容的指纹：能猜内容的人可以自己算一遍来**确认**
（"这条消息大概是『好的』"）。所以 `frameIdOf(sessionId, record, {key})` 把房间密钥
掺进哈希 —— 两端（都持有密钥）算出来一致，**没有密钥的人算不出 id**，
而 id 的作用（两端去重、中继按它去重）一点没少。没给密钥时行为与从前一字不差。

### 3. 打不开就**报错**，不静默丢

拉到密文帧而这次没给 `--key`：`openFrame` 抛一句人话（"这一条是加密的，但这次同步
没给房间密钥"）。**静默跳过**的后果是"另一端的历史少了一段，而两边都不知道"。

### 4. 密钥从哪来：房间链接的 fragment（**不落盘、不进服务端**）

`ding sync ... --key <base64url>`（或环境变量 `DH_SYNC_KEY`）。密钥由主人在建房间时
拿到（`ding space room` / 设置页那两处都只显示一次），经**链接的 `#`** 交给另一端 ——
服务端从来收不到它（`parseRoomLink` 只认 fragment，query 里那份不算）。

**如实记边界**：这一层**不给密钥管理**（怎么安全地把密钥交给另一端是人的事）；
密钥轮换 = 换房间（ADR-0016 §2）；大内容（>64KB）仍不同步（ADR-0016 §3）。
