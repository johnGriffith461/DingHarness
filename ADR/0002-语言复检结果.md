# ADR 0002：语言路线复检（按 perf-budget 实测）

- 日期：2026-10-15
- 状态：**已决（维持路线 A）**
- 依据：方案《V4 后续篇》§3 的复检程序 + Phase 10.5 的实测数字
- 数字来源：`engine/eval/perf-baseline.md`（由 `pnpm perf:budget` 生成，可复现）

## 背景

§3 把语言路线**定案为 A**（维持 TypeScript/Node + Bun 单二进制分发 + Rust 沙箱旁路），
并留了一道**防僵化**的复检程序：

> Phase 10.5 按 perf-budget 实测一次 —— 仅 CPU 项不达标 → 路线 C 单点旁路；
> **四项中 ≥3 项不达标 → 重开 B 评估并出 ADR**。默认结论不变，除非数字说话。

Phase 10.5 做完了，数字在这儿（本机 Windows、Node 24.18、测于 2026-10-15）：

| 指标 | 实测 | 方案预算 | 结论 |
|---|---|---|---|
| CLI 冷启动 | ~355–407 ms（多次采样） | ≤ 100 ms | **不达标** |
| CLI 常驻内存 | ~84–93 MB | ≤ 50 MB | **不达标** |
| 10 并发回合 · 内存增长 | ~6–8 MB | ≤ 200 MB | 达标 |
| 10MB 日志 token 估算 | ~210–250 ms | ≤ 500 ms | 达标 |
| 10 并发回合 · 编排 CPU | 每回合 33–48 ms | 方案写"利用率 ≤ 5%" | **口径不同，不直接判** |

## 判定

1. **"四项中 ≥3 项不达标"不成立** —— 明确不达标的是两项（冷启动、常驻内存），
   两项达标（内存增长、token 估算）。按程序**不重开路线 B 评估**。
2. **"仅 CPU 项不达标"也不成立** —— 因为 CPU 那条**没法判**：
   方案写的是"稳态利用率"，而我们能测的是"突发口径"（10 个回合跑完就算完），
   而且假 provider 与压测同进程、它的 CPU 也算在里面。
   拿一个口径不同的数字去判"达标/不达标"，就是在用数字凑结论 —— 那正是这张表要避免的事。
3. 所以**默认结论不变：维持路线 A**。

## 那两项超预算怎么算

**如实记下来，不修饰，也不找借口**：

- **冷启动 407ms 里含 Node 自身的启动时间**。方案 11.1 的验收形态是 Bun 编译的
  **单文件可执行**（已交付），那个形态的冷启动是另一条路（`verify-cli-bin.mjs` 量到 ~285ms，
  同样含 runtime 启动）。这一条要真正达标得靠"预热/常驻"这类产品形态变化，
  不是靠换语言能解决的 —— 而"换语言"的代价在 §3 里已经论证过（插件生态、桌面宿主、单向门）。
- **常驻内存 84MB** 里大半是 Node 运行时与 SDK 的地基。降到 50MB 以下意味着重写运行时依赖，
  而那换来的用户可感知收益是"少几十兆内存" —— 按 §3 的论证，这不值得用可逆性去换。

## 什么时候该重开这个决定

按 §3 的程序，出现下列**证据**再回来（不是"感觉慢了"）：

1. 四项里 ≥3 项实测不达标（同样的口径、可复现的数字）；
2. 出现"只有换语言才能解决"的用户级需求（例如单二进制必须 < 50MB 且不能带 runtime、
   或需要与 Rust 生态深度互操作）；
3. CPU 那条**用稳态口径**测出来确实超标（那时它是"仅 CPU 不达标" → 走路线 C 单点旁路，
   不是重开 B）。

## 影响

无代码变更。这一条的价值在于：**把"我们量过、结论是维持"这件事写下来** ——
否则半年后会有人再问一遍"要不要用 Rust 重写"，而那次不会有数字。
