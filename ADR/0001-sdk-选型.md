# ADR 0001：AI SDK 的取舍 —— 保留 Vercel AI SDK（选项 A）

- 状态：**已决定**（2026-10-15）
- 相关：[Phase 5.2 协议分层](../../engine/runtime/protocols/)、[Phase 6 PoC 脚本](../../scripts/poc-sdk.mjs)

## 背景

引擎的模型调用层基于 Vercel AI SDK v7（`ai` + `@ai-sdk/openai-compatible`）。
方案要求"更换 AI SDK 是重大决策，**先评后换**"，三项指标：
① prompt caching 可控性；② 工具调用的确定性；③ 中止 / 重试 / 步数语义完备性。

三个候选：

| 选项 | 做法 | 适用 | 代价 |
|---|---|---|---|
| **A（本 ADR 的决定）** | 保留 AI SDK，协议扩张走官方 provider 包 | 求稳、想快 | 受 SDK 抽象上限约束 |
| B | LiteLLM（proxy 或 SDK）统一百家 provider | 要最大覆盖面 | 多一层代理/运维；loop 语义需重新验证 |
| C | 直连各家原生 SDK，自写 loop 适配 | 要完全控制 | loop 层重写 + 长期维护成本 |

## 证据（`node scripts/poc-sdk.mjs`，全程打在本地假端点，不发一次真请求）

| 指标 | 结论 | 实测 |
|---|---|---|
| ① prompt caching 可控性 | **通过** | 三种写法（调用级 `providerOptions`、消息分片级、系统提示词 + 分片级）**都**把 `cache_control: {type:"ephemeral"}` 真的序列化进了请求体 |
| ② 工具调用的确定性 | **通过** | 同一输入跑两遍，工具调用的名字与参数序列完全一致；一帧里的两个并行调用都保留且按到达顺序 |
| ③ 中止 / 重试 / 步数 | **通过** | 中止 → `aborted=true` 且 `ok=true`（中止不算 provider 失败）；`maxSteps=3` 实测 3 步；工具报错作为 `tool-result` 回注、整轮不中断 |

三项全通过 → **按方案规则停在选项 A**，不强行换 SDK。

## 这个 PoC 顺带逮到的两个真问题

写评估脚本的价值有一半在这里 —— 它们都不是"SDK 行不行"，是**我们用错了**：

1. **步数统计一直是错的**。主循环原来只认 `finish`（那是**整轮结束**），
   而 AI SDK 的每步边界是 `finish-step`。于是 `maxSteps=3` 的一轮也只发 1 个
   `step-finish`，子智能体的"几步"靠 `工具调用数 + 1` 兜底（近似值）。
   已修：认 `finish-step`；末尾的 `finish` 只作兜底（万一某个 provider 不发每步事件）。
   ⚠️ 这件事**测试原来测不出来**：单步场景下 `finish` 与 `finish-step` 数目相同。
   PoC 特意用"每步都调工具"的假端点，才把它照出来。

2. **Anthropic 的 baseURL 必须带 `/v1`**。SDK 是**直接拼** baseURL 的：
   不带 `/v1` 时它发到 `/messages`，而真实端点在 `/v1/messages` → 404。
   provider 表里 anthropic 那条写的是 `https://api.anthropic.com/v1`（已核实过的写法）。

## 决定

**选项 A：保留 AI SDK v7，协议扩张走官方 provider 包**（`@ai-sdk/anthropic`、`@ai-sdk/google`）。

理由：
- 三项指标的实测结论都支持"够用"（尤其 caching —— 那是选项 A 最容易被质疑的一点）；
- Phase 5.2 已经把协议差异关进 `engine/runtime/protocols/`，**加一家 provider = 加一条配置**，
  加一种协议 = 加一个 adapter 文件，主循环一行不动；
- B 要多一层代理（运维成本 + 一层语义需重新验证），而我们的痛点是"协议覆盖"而不是"家数"；
- C 要重写 loop，而 loop 里已经有事件流、用量、健康记账、闸门回注这些必须保住的语义。

## 硬约束（换不换 SDK 都成立）

`engine/ports`（store / health / executor）与 `TurnEvent` 契约**不变**。
宿主、CLI、验收快照因此全部零感知 —— 这个 PoC 与 Phase 5.2 的协议分层都没有动它们一行。

## 后果

- 协议分层落地后，**新协议的验收方式**是：加一个 adapter + 让 `scripts/poc-sdk.mjs`
  用那个协议的假端点跑一遍三项指标。**没有真协议端点就不算接上了**（只有配置不算）。
- 什么时候该重开这个决定：出现"官方 provider 包覆盖不到的协议"，
  或需要 SDK 给不了的控制（例如自定义流式协议、原生思考块的非标准字段）。
  那时**优先考虑给 SDK 提 PR 或写自定义 provider**（它支持），而不是换掉整个 SDK。
