## 背景

V5-2 的同步层要回答一个问题：**两个端（比如本机 + 手机）怎么把同一段会话的事件
彼此送达、且不漏不重不打架**。V5 §4 定了三条口径：中继承担协调职责、本地 SQLite
保持数据权威、并发接管带 fencing。

这一轮（2.1）冻的是**协议语义**，并把中继 core 与 HTTP 端点落地；
真正的双设备产品形态（配对码、成员 token、E2EE）是 2.2–2.6 与 V5-3 的活。

## 决定

### 1. append-only + offset 游标

事件按**流**组织（一条流 = 一个同步单元，比如一段会话）。每条记录在流里有一个
从 1 起的 `offset`：**单调、永不复用**。读的唯一方法是 `pull({from})` ——
游标是 offset，不是"最后一条的 id"（id 会在重发里出现两次，offset 不会）。

### 2. exactly-once producer：`(producerId, epoch, seq)`

每条事件带 producer 三元组：

- `producerId`：谁产的（一端一个）；
- `epoch`：**令牌世代**（接管一次 +1，见第 4 条）；
- `seq`：这个 producer **在这个 epoch 里**的序号，从 1 连续。

中继按 `(producerId, epoch)` 记"已收到的最高 seq"：重发 ≤ last 的**幂等跳过**
（返回 `duplicates` 计数，不报错）。**跳跃**（> last+1）→ **整批拒绝**并给出
`expected`（缺一条就是缺一条，中继不猜）。

**推的失败不动客户端游标**：下一轮重推同一批（seq 一样 → 中继去重）。

### 3. 事件 `id`：跨 epoch 的去重身份（实现期发现的那条）

`(producer, epoch, seq)` 只在一个 epoch 内成立。**接管换 epoch 之后 seq 从头编**，
于是"ack 丢了、接管之后重发"会被当成新事件 —— 这就是重复。

所以：**本地出站队列给每件事分配一个稳定 `id`**，中继按 id **跨 epoch 去重**（已实现并有测试）。
没有 id 的批次，在"接管 + ack 丢失"并发下可能重复 —— 真客户端必须带 id（见 Open follow-ups）。

### 4. fencing：接管换令牌，旧令牌的写入被**明确拒绝**

`claim(stream, holder)` 把 epoch +1 并返回新令牌；`push` 必须带**当前** epoch，
否则回 `fenced`（附"请重新 claim"）。被 fence 的那批**没有进流** ——
不是"收下但没人看"（后者会让两端都以为自己成功了）。

这是防脑裂的唯一屏障：没有它，接管之后老那一端还在写，两边的事件会交错成
谁也无法解释的历史（FastClaw 沙箱租约那条实测算是最贵的教科书：
"10 pods → 10 e2b instances"）。

HTTP 上：`fenced` / `gap` / `too-large` 一律 **409**（请求本身没毛病，是状态不允许）
—— 与"参数不对 = 400"分开，调用方按 `code` 分流。

### 5. 大内容走引用通道

单条事件的内联载荷上限 **64KB**（`MAX_INLINE_BYTES`）。超限**拒收**并说清"改用引用"
（`payload: {ref:{id,bytes,mime?}}`）；引用形态本身很小、不受限。

理由：流是"发生了什么"的索引，不是文件柜 —— 一张 2~3MB 的生成图内联进来，
一次 pull 就把它整份灌给每个端（而生成图本来就落盘 + `dshasset://` 引用，见 P20 那条）。

### 6. 两端游标：两个数字，可持久化

`CursorState = {streamId, producerId, epoch, pushedSeq, pulledOffset}` ——
**只有数字与 id**（没有句柄、没有时间戳），宿主存进本地库（2.6 与崩溃恢复统一）。
重连 = 用同一个 epoch + 接着编的 seq 重推（**精确去重**）；被接管过 → `fenced` →
重新 claim（此时 seq 归零、新账）。

⚠️ **游标按 `accepted + duplicates` 前进**（这一点被测试纠过）：全被去重的重发
（accepted 0、duplicates 2）说明那两条**已经在中继里**，只按 accepted 走会让
下一条被编成早已收过的 seq，于是"补完重发之后的新事件"永远推不上去。

### 7. 端点形状（与 Phase 17 Agent Server 合并演进）

| 方法 | 路径 | 干什么 |
|---|---|---|
| `PUT` | `/v1/streams/<流>` | 建流（幂等；id 形状与 sessionId 同一套） |
| `POST` | `/v1/streams/<流>/claim` | 接管，返回新 epoch |
| `POST` | `/v1/streams/<流>/push` | 推一批（`{producerId, epoch, events[]}`） |
| `GET` | `/v1/streams/<流>/pull?from=&limit=` | 从游标拉 |
| `GET` | `/v1/streams/<流>` | 流的状态（诊断） |

**没接线就 501**（与 `/v1/sessions` 同一口径：不假装一条空流）；
鉴权与其余端点**完全一样**（新端点不是后门 —— 有断言钉着）。

## 明确不做的

- **不让中继当数据主人**：它不落盘、不解释事件内容、不做保留策略 ——
  "这段会话的真相"永远在本地 SQLite（V4 不变量）。中继重启丢的是**传输窗口**，
  不是数据（客户端 offset 游标决定补投范围）。
- **不做中继侧的多实例一致性**（Raft/共识那一套）：本机版一次只有一个中继进程；
  "多实例竞态"在本轮指的是**两个端并发接管**（已测），不是多台中继互相抄。
  真要做多台中继时，那是"中继持久化 + 共识"的一次单独设计（见 follow-ups）。
- **不在协议层做权限判定**：谁能进哪条流是 2.2（成员 token）与 V5-3 的事；
  本轮中继只管"按序、恰好一次"。

## 后果

- 两端同步有了可测的语义：三态（乱序/重复/断线重连）、fencing、多端竞态
  逐条有 fixture；HTTP 那一层只是搬运（协议语义一个字不重写）。
- 实测过的两处真实缺陷（都修了并留了回归）：
  · 路径里的**坏百分号编码**原来会 500（`decodeURIComponent` 抛 URIError）——
    现在三条路（sessions/streams/hooks）都走 `safeDecode` 回 **400**；
  · 游标在"全被去重的重发"之后不前进 → 后续新事件永远推不上去（见第 6 条）。
- 已知边界（如实记）：中继不持久化；没有 id 的事件在跨 epoch 场景可能重复；
  多台中继未设计。
