## 背景

`ding serve` 此前只有**单口令**：知道口令就是"主人"，不知道就是 401 ——
它能回答"能不能用"，回答不了"**是谁**在用"。V5-2 要在这上面长出协作能力
（按人过滤、事件带 actor、撤权），第一件事就是把身份认出来。

## 决定

### 1. 两种凭据并存：主口令（主人）+ 成员口令（成员）

| 凭据 | 身份 | 权限 |
|---|---|---|
| `--token` / `DH_SERVE_TOKEN`（或现场生成的） | `{id: "local", owner: true}` | **全权**（与从前逐字相同） |
| `--member <id>:<口令>`（可重复） | `{id: <成员 id>, owner: false}` | 受限（见下） |

**认证机制一个字不改**：同一个 `sameToken`（sha256 摘要 + `timingSafeEqual`）、
同一条 401 路、同一套限速。变的只是"认出来之后知道你是谁"。

⚠️ **候选全比一遍再决定**（`identify` 不提前 return）：提前退出会让"匹配上的是第几个成员"
从耗时里漏出去 —— 与常数时间比较是同一条纪律的两半。

### 2. 成员口令**不自动生成**

主口令不给时会现场生成并打印（本机主人必须有钥匙）；成员口令**必须显式给** ——
生成出来的也得打印，而"打印多份凭据"是坏习惯（何况每个成员该有自己的口令管理）。

### 3. 归属过滤（2.2 的验收那条）

`GET /v1/sessions`：

- **成员**：默认（不给 `?owner=`）**只列归自己的**；指定别人的 owner → **403**
  （带一句人话，不是"悄悄过滤成空列表" —— 那会让人以为对方没有会话）；
- **主人**：不给参数列全部（老口径），给了 `?owner=` 就过滤。

归属缺省按兼容口径 `local` 读（旧会话补列之前没有这一格 —— C1 的迁移口径）。

### 4. 坏配置**启动就拒**（fail fast）

重复 id / 空 id / 空口令 / 成员口令与主口令相同 → `startAgentServer` 直接抛
（带一句说清怎么改的话）。等到有人请求才发现，等于把配置错误伪装成认证失败 ——
而认证失败会触发限速，排查方向整个跑偏。

### 5. 主口令优先

理论上成员 id 可以叫 `local`，那样"主人身份"会变得含糊。所以匹配时**主口令先判**：
拿着主口令的人一定是主人，成员口令不会把主人挤掉。

## 明确不做的

- **不做成员表的持久化**（还是宿主注入）：它该与"团队空间/邀请"一起落（V5-3 3.1），
  现在先有个跑得起来、测得到的形态；ADR-007 的 follow-up 里记着这件事。
- **不在这一层做角色判定**：`owner/admin` 能不能查别人的会话、`viewer` 能不能调写端点 ——
  那是 C2 的两轴判定（ADR-007），要等成员表带上 roles。**现在一律"成员只能碰自己的"**，
  这是最保守的一侧，V5-3 只会放宽、不会收紧。
- **不改任何既有安全口径**：loopback 默认、对外必须显式 token、Host/Origin/Sec-Fetch 白名单、
  请求体上限、认证失败限速 —— 测试里逐条还在。

## 后果

- 服务端第一次知道"是谁在请求"：`/v1/info` 回 `you`（调用方可以自证身份）、
  `/v1/sessions` 按归属过滤、2.3 的 SSE actor 有了来源。
- 单人使用零变化：只给 `--token` 时行为与从前逐字相同（测试里有对照）。
- 已知边界（如实记）：成员**没有角色**（一律最保守）；成员表在内存里（重启要重新给 `--member`）；
  成员只能列会话 —— 中继端点（2.1）的 per-member 授权要等 V5-3。
